# claims_assistant_project
An insurance claim adjudication assistant

1. core/ (The Foundation)
This directory defines the rules, settings, and data structures the entire application must follow. It prevents the system from passing bad data between agents.

config.py

Description: Manages all environment variables (API keys, database URLs, LLM model names).

Logic: Uses Pydantic to enforce type safety. If the system boots up missing the OpenAI key, the application crashes immediately with a clear error, rather than failing silently mid-process.

Links To: Imported by document_parser.py, extractionagent.py, liabilityagent.py, and formattingagent.py.

models.py & state.py (Implied/Defined in main)

Description: Defines the Pydantic schemas (e.g., ExtractedFacts) and the LangGraph ClaimState dictionary.

Logic: This is the "shared memory" of the system. It enforces a strict JSON structure so that Agent A knows exactly what data shape to expect from Agent B.

Links To: Used by main.py to initialize the graph and imported by all agents to validate their outputs.

2. ingestion/ (The Pre-Processing Pipeline)
This directory handles the raw, messy real-world data before the multi-agent reasoning loop ever begins.

document_parser.py

Description: Connects to AWS Textract (OCR) to convert scanned PDFs or handwritten notes into raw string text.

Logic (PII Scrubbing): Uses Regex to mask sensitive data (Social Security Numbers, phone numbers) before it hits the LLM. This solves the problem of leaking user privacy to third-party AI models.

Links To: Runs independently to populate the raw_text field in the initial ClaimState before calling main.py.

chunking_strategy.py

Description: Slices the extracted text into sections for the Vector Database.

Logic (Parent-Child Strategy): Instead of slicing text blindly by character count, it groups text by structural sections (e.g., "Driver A info", "Officer Narrative"). It splits the narrative into sentences (children) for precise database searching, but maps them back to the full paragraph (parent) so the LLM gets full context.

Links To: Feeds the Qdrant database (which is queried by the ragretriever.py tool).

3. tools/ (The Agent Capabilities)
Agents are just brains; tools are their hands and eyes. These files allow the LLM to pull deterministic, real-world data to prevent hallucinations.

ragretriever.py

Description: Connects to the Qdrant vector database to find similar past claims or internal company guidelines.

Logic (Hybrid Search): Uses both dense vector search (for conceptual matching like "who is at fault") and sparse BM25 keyword search (for exact matches like a specific claim ID). It merges the results to provide highly accurate context.

Links To: Imported and executed exclusively by liabilityagent.py.

policylookup.py

Description: A deterministic database lookup for specific state traffic codes.

Logic: LLMs are notorious for inventing fake laws (hallucinations). By forcing the agent to use this tool to look up a citation (e.g., "Failure to Yield in IL"), it retrieves the exact legal text, ensuring the final decision is legally sound.

Links To: Imported and executed exclusively by liabilityagent.py.

4. agents/ (The Reasoning Engine)
These files represent the distinct "workers" in the LangGraph orchestration. Each has a highly specialized prompt.

supervisor.py

Description: The router. It does not use AI; it uses hardcoded logic.

Logic: It reads the ClaimState. If extracted_facts is empty, it outputs route_to: extraction. If facts exist but liability_decision is empty, it outputs route_to: liability. It acts as the traffic cop ensuring processes happen in order.

Links To: It receives the output of all other agents and dictates the next move in main.py.

extractionagent.py

Description: Data miner.

Logic: Uses a fast, cheap LLM model configured for strict JSON output. Its sole purpose is to read the messy raw_text and output the ExtractedFacts Pydantic model. It makes zero decisions about fault.

Links To: Called by the Supervisor. Passes updated facts back to the Supervisor.

liabilityagent.py

Description: The adjudicator.

Logic: Uses the heaviest, smartest LLM model. It takes the facts from the Extraction agent, queries the tools/ to get laws and precedents, and then reasons through the collision dynamics to assign a fault percentage.

Links To: Called by the Supervisor. Uses tools. Passes the liability decision back to the Supervisor.

formattingagent.py

Description: The reporter.

Logic: Takes the cold JSON logic generated by the Liability agent and translates it into a polished, human-readable summary for a human insurance adjuster to read on a dashboard.

Links To: Called by the Supervisor. Ends the process.

5. The Orchestrator
main.py

Description: The execution script that wires the entire graph together.

Logic (LangGraph StateGraph): It creates the workflow object. It registers every agent as a "node." It creates "edges" (the paths between nodes). Crucially, it sets up a conditional edge on the Supervisor node—meaning the graph dynamically changes its path based on the state of the claim.

Links To: It imports ClaimState, all agents in agents/, and triggers the loop.

The Overall Execution Flow (How it solves the problem)
Start: main.py initializes the ClaimState with raw text from a police report and sends it to the supervisor_node.

Evaluate 1: The Supervisor sees there are no facts. It routes to extraction_node.

Extract: extractionagent.py uses an LLM to parse the messy text, finds that Driver B was speeding, and updates ClaimState["extracted_facts"]. The loop forces it back to the Supervisor.

Evaluate 2: The Supervisor sees facts exist, but no liability decision exists. It routes to liability_node.

Adjudicate: liabilityagent.py reads the facts, uses policylookup.py to pull the speeding law, decides Driver B is at fault, and updates ClaimState["liability_decision"]. The loop forces it back to the Supervisor.

Evaluate 3: The Supervisor sees facts and liability are complete. It routes to formatting_node.

Finish: formattingagent.py writes a clean paragraph summarizing the claim. The graph hits the END node, and the process completes, delivering a fully audited, hallucination-free JSON payload.
